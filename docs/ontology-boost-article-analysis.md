# Ontology Boost 記事整理とモック反映状況

作成日: 2026-06-10  
対象記事: [生成AIに「御社の業務知識を授ける」。知識基盤「オントロジー」構築・運用支援サービス「Ontology Boost（オントロジーブースト）」提供開始](https://prtimes.jp/main/html/rd/p/000000055.000082787.html)

---

## 1. 記事の概要

株式会社SiNCEは、生成AIが企業固有の業務知識を正しく理解するための知識基盤を構築・接続・運用するサービス「Ontology Boost」を提供開始した。

記事の中心メッセージは、生成AIに業務知識を「覚えさせる」のではなく、LLMの外側に企業専用の知識辞書・知識基盤を整備し、回答時にAIが参照できるようにすること。

これにより、ChatGPT、Claude、Geminiなどの生成AIが、企業固有の用語、KPI、業務ルールに沿って、根拠を示せる回答を行えるようにすることを狙っている。

---

## 2. 記事で述べられている課題

記事では、生成AI活用が進んでも企業でAI導入がうまく進まない理由として、AIの性能不足ではなく「自社固有の業務知識がAIの読める場所に存在しない」という構造的な課題を挙げている。

主な課題は以下。

- 生成AIは一般知識には強いが、企業固有の業務知識、判断基準、KPI、用語、業務ルールを最初から理解しているわけではない。
- 社内の知識が文書、資料、経験者の暗黙知、部門ごとのルールとして散在しており、AIが参照可能な形に整理されていない。
- その結果、AIの回答が「それっぽい」内容にとどまり、業務判断に使うには根拠や社内文脈が不足する。

---

## 3. Ontology Boost の考え方

Ontology Boostは、オントロジーを「構築・接続・運用」まで一貫して支援するサービスとして紹介されている。

重要な考え方は以下。

- LLMの外側に企業専用の知識基盤を置く。
- AIに知識を覚えさせるのではなく、回答のたびに参照させる。
- 企業固有の用語、KPI、業務ルール、判断基準をAIが扱える形に構造化する。
- 利用を重ねるほど、企業専用の知識が蓄積・更新される。
- 文書化されにくいベテランの感覚や判断基準も、Hearing AIなどを通じて構造化・蓄積する。

記事では、Databricks Unity Catalog / Genie / Vector Searchとの連携にも触れられており、最短4週間で企業専用の知識基盤の蓄積を開始できるとしている。

---

## 4. 期待される効果

記事で示されている導入後の効果は以下。

- 経営: AIが出した数字や回答を会議資料に使いやすくなり、根拠確認の往復を減らせる。
- 組織: ベテランの判断基準を組織に残し、属人化を減らせる。
- 継続: 新しいLLMが登場しても、企業の知識資産は外部の知識基盤として引き継げる。
- 回答品質: 「それっぽい回答」から「判断に使いやすい回答」へ変えられる。

---

## 5. 現在のモックに反映されていること

現在の「迷わせないレコメンド」モックには、Ontology Boostの記事で語られている考え方の一部がすでに反映されている。

### 5.1 LLMの外側に知識基盤を置く設計

モックは、Neo4jのナレッジグラフとJSON設定ファイルを使い、ユーザー回答、価値観、Need、Load、サービス候補を構造化して扱っている。

該当する実装:

- `graph/graph_builder.py`
- `api/demo/graph_path_service.py`
- `config/service-offerings.json`
- `config/kg-need-links.json`
- `config/need-mapping.json`

記事の「覚えさせるのではなく、参照させる」という思想に近い。

### 5.2 用語・概念をオントロジー的に整理している

モックでは、以下の概念が分離されている。

- 価値観プロファイル
- Need
- Load
- Capability
- ServiceOffering
- DecisionStyle
- 推薦サービス
- 推薦理由

これは、記事でいう「企業固有の業務知識をAIが読める形に整理する」方向性と一致している。

### 5.3 根拠を示せる推薦

サービス推薦では、単におすすめを出すだけでなく、以下の根拠を表示している。

- 価値観プロファイル
- 関連ニーズ
- 懸念事項
- 推薦サービス
- Need / Load / Value のマッチ状況
- 「なぜこの提案か」の説明ページ

該当する実装:

- `demo-web/src/components/demo/ServiceReasoningClient.tsx`
- `demo-web/src/components/demo/ServiceKnowledgeGraph.tsx`
- `demo-web/src/components/demo/ServiceOfferingSection.tsx`

記事の「根拠を示せる回答」「判断に使いやすい回答」に近い体験になっている。

### 5.4 利用ログによる知識の蓄積

モックには、セッションログ・推薦サービス・フィードバックを蓄積する仕組みがある。

記録している主な内容:

- セッションID
- 価値観プロファイル
- 抽出されたニーズ
- 抽出された懸念事項
- 推薦サービス
- サービスへのフィードバック

該当する実装:

- `api/demo/analytics_logger.py`
- `data/demo/logs/session_analytics.jsonl`
- `demo-web/src/app/demo/analytics/page.tsx`

これは、記事の「利用を重ねるごとに知識が蓄積・更新される」という考え方に近い。

### 5.5 フィードバックを推薦ロジックへ反映

モックでは、過去ログ内の類似価値観プロファイルのフィードバックを使って、次回以降の推薦スコアを調整する仕組みが入っている。

例:

- 類似ユーザーが特定サービスに「合わない」と回答した場合、そのサービスの適合度を下げる。
- 「少し気になる」「詳しく知りたい」が多い場合は、適合度を上げる。

該当する実装:

- `api/demo/analytics_logger.py`
- `engine/service_recommendation_engine.py`
- `api/demo/router.py`

これは、記事の「使うほど成長する」に対応するモック上の学習表現になっている。

## 6. 現在のモックにまだ反映されていないこと

記事の内容のうち、現在のモックに未反映、または表現が弱いものは以下。

### 6.1 業務知識の構築・接続・運用をワンストップで支援する画面

記事では、Ontology Boostがオントロジーの「構築・接続・運用」まで支援するとされている。

現在のモックでは、ユーザー向けの推薦体験が中心であり、オントロジーそのものを構築・編集・運用する管理画面はない。

未反映の例:

- 業務用語を登録・編集する画面
- Need / Load / Service / Capability の関係を編集する画面
- ナレッジグラフの更新履歴を見る画面
- 承認フロー付きの知識更新画面

### 6.2 社内資料・散在資料から知識を取り込む体験

記事では「完璧なデータ基盤は不要」「今ある散在資料から始められる」とある。

現在のモックでは、サービスカタログや設定JSONは存在するが、ユーザーが資料をアップロードして知識化する体験はない。

未反映の例:

- PDF / Excel / PowerPoint / 議事録から用語・ルール・判断基準を抽出する画面
- 取り込んだ知識を確認・修正する画面
- 既存資料からNeedやServiceOfferingを自動生成する流れ

### 6.3 Hearing AI による暗黙知の構造化

記事では、文書化されにくいベテランの「感覚」や「判断基準」を音声インタビューから構造化・蓄積する「Hearing AI」が強みとして紹介されている。

現在のモックには、音声インタビューや会話ログから判断基準を抽出する機能はない。

未反映の例:

- ベテラン営業へのヒアリング画面
- 音声・テキストインタビューから判断基準を抽出する機能
- 抽出した暗黙知をNeed / Load / Service / Sales Talkへ反映する流れ

### 6.4 Databricks Unity Catalog / Genie / Vector Search 連携

記事ではDatabricks連携が明示されている。

現在のモックはNeo4j、JSON、FastAPI、Next.jsで構成されており、Databricks系の連携はない。

未反映の例:

- Unity Catalog上のデータ資産との接続
- Genieによる自然言語問い合わせ
- Vector Searchによる文書検索・根拠文書検索

### 6.5 KPI・業務ルールに沿った回答

記事では、企業固有のKPIや業務ルールに沿った回答を引き出すことが強調されている。

現在のモックでは、価値観、Need、Load、サービス適合度は扱っているが、企業KPIや業務ルールを明示的に制約条件として扱う設計は弱い。

未反映の例:

- KPIを登録する画面
- KPIに対する推薦の貢献度表示
- 「この提案はどの業務ルールに基づくか」の表示
- ルール違反・制約違反の検知

### 6.6 複数LLMにまたがる知識資産の継続利用

記事では、ChatGPT、Claude、Geminiなどの主要生成AIで、同じ知識基盤を参照できることが示されている。

現在のモックは、推薦エンジンと一部テンプレート・API中心であり、複数LLMを切り替えて同じオントロジーを参照する体験はない。

未反映の例:

- LLMを選択するUI
- 同じ知識基盤を複数LLMに接続する設計
- LLMごとの回答比較

### 6.7 経営・組織・継続という導入効果のストーリー化

記事では、導入後の効果として「経営」「組織」「継続」の3観点が示されている。

現在のモックは顧客向けの推薦体験に寄っており、経営者・管理者向けに「導入すると何が変わるか」を示す画面は弱い。

未反映の例:

- 管理者向けダッシュボード
- 属人化削減の可視化
- ナレッジ蓄積量の推移
- 推薦精度やフィードバック改善率の推移

## 8. モックに追加すると記事内容との整合性が高まる機能案

### 優先度A: すぐに反映すると分かりやすい

1. 「業務知識基盤」画面の追加
   - 登録済みのNeed、Load、Service、Capabilityを一覧表示する。
   - それぞれの関係を「知識辞書」として見せる。

2. 「知識が育つ」表示の強化
   - ログ件数、フィードバック件数、改善された推薦件数を可視化する。
   - 「このサービスは過去のFBによりスコア調整されました」と表示する。

3. 提案理由に「参照した知識」を明示
   - 例: 「参照した知識: Need=静かな空間で移動したい / Load=情報過多による判断負荷 / Service=オーディオスマートチューニング」
   - 記事の「根拠を示せる回答」に直結する。

### 優先度B: デモの説得力が上がる

4. 社内資料取り込みモック
   - ExcelやPDFをアップロードしたように見せ、サービス候補や業務ルールが抽出される画面を追加する。

5. ベテラン営業ヒアリングモック
   - テキスト入力で「ベテランの判断基準」を登録し、Need / Load / Sales Talkに変換する流れを見せる。

6. 管理者向けダッシュボード
   - 知識数、FB数、改善率、よく出る懸念事項、評価の低いサービスを表示する。

### 優先度C: 記事の技術要素に寄せる

7. KPI・業務ルール設定
   - 例: 「問い合わせ率を上げる」「不要提案を減らす」「説明可能性を担保する」などをKPIとして持つ。

8. 外部ナレッジ連携の表現
   - Databricks連携そのものは実装しなくても、将来連携先として「Catalog」「Vector Search」「CRM」などを画面上に表示する。

## 9. このモックの位置づけ

現在のモックは、Ontology Boostの記事でいう「業務知識をAIの外側に置き、根拠ある判断に使う」という思想のうち、特に以下を自動車・サービス推薦領域に落とし込んだものと位置づけられる。

- 顧客回答を価値観・ニーズ・懸念事項に構造化する。
- 構造化された知識をもとにサービスを推薦する。
- なぜその提案なのかを可視化する。
- ユーザーのフィードバックを蓄積し、次回以降の推薦に反映する。

一方で、記事が訴求している「業務知識基盤そのものを構築・接続・運用するサービス」として見せるには、知識の登録・更新・運用・暗黙知抽出・KPI連携の画面がまだ不足している。

---

## 10. 結論

現在のモックは、Ontology Boostの思想のうち「構造化された知識を参照して、根拠ある推薦を行う」部分はかなり反映できている。

特に、価値観プロファイル、Need、Load、サービス候補、ナレッジグラフ、フィードバックログ、推薦スコア調整は、記事の「AIに業務知識を参照させる」「使うほど成長する」という主張と相性が良い。

今後、記事内容との一致度をさらに高めるなら、次の3点を優先するとよい。

1. 知識基盤の中身を見せる管理画面
2. 過去ログ・フィードバックによって推薦が変化したことの可視化
3. ベテラン判断や社内資料を取り込んで知識化するモック
